# Testing

Commander Keen games and mods are copyrighted, so none of them are in the
repository. Tests come in three layers.

`pnpm test:all` (`scripts/test-all.mjs`) runs everything CI runs plus all
ignored Rust tests below, keeps going after a failure and lists the failed
steps at the end. Use it before a release or after broad changes; it expects
the games, mods and DOSBox in `.local` (see the script for the variables that
override the paths).

## 1. Unit tests (CI, every push)

```sh
pnpm test            # frontend (Vitest, components via Testing Library)
cd src-tauri && cargo test
```

They use small synthetic fixtures and need nothing else. `cargo test` in
`src-tauri` covers the whole workspace: the app and the `keen-saves` and
`keen-graphics` crates. CI (`.github/workflows/ci.yml`) also runs lint,
format, typecheck, clippy and the frontend build, and fails if
`src/bindings.ts` (regenerated by `cargo test`) is out of date. Pushes are
checked on Linux; starting the workflow by hand checks Windows and macOS too.

The KeenWiki parser (`src-tauri/src/keenwiki.rs`) is tested against saved
pages in `src-tauri/tests/keenwiki/` (several mod pages, a game page and a
missing page; `README.md` there lists their sources). When the wiki markup changes, save the page
again with an honest `User-Agent` (one request per page) and update the
expectations.

The saved game parser is its own crate (`src-tauri/keen-saves`, part of the
workspace, so plain `cargo test` runs it). Its fixtures in
`keen-saves/tests/fixtures/` are real saves made by playing: Keen 1-3 whole
(92 bytes), Keen 4-6 and Keen Dreams cut right after the game state, so no
level data from the games is in the repository.

The title screen extractor is its own crate too (`src-tauri/keen-graphics`).
Its tests build the formats from hand-made data; real game files only come in
through the ignored tests below.

## 2. Mod corpus (CI weekly, or locally)

`src-tauri/tests/mod-corpus.json` lists real mods: their download URL on the
KeenWiki file server, SHA-256 and what BloogBase should detect (game, name,
start recipe, game versions). The test downloads missing archives once into a
cache and compares.

```sh
cd src-tauri
cargo test --lib corpus -- --ignored --nocapture
```

(`--lib` keeps the `keen-graphics` corpus test below out of the run.)

- Cache: `BLOOGBASE_MOD_CACHE`, default `.local/mods`.
- Adding a mod: append `{ "url": "…" }` to the manifest, put the archive into
  the cache, then run with `BLOOGBASE_CORPUS_UPDATE=1` to fill in the hash and
  expectations. Review the diff before committing.
- After a change to the heuristics, a failing entry means a real mod is now
  detected differently: fix the code or, if the new result is better, update
  the manifest the same way.
- CI (`.github/workflows/mod-corpus.yml`) runs it weekly and whenever the
  manifest changes, with the archives cached so the community's file server
  isn't hit on every run.

## 3. Local tests with real games (before a release)

These are ignored tests that need the games, which can't be in CI. The title
screen tests expect game folders named `keen1` … `keen5`, plus `keen6`
(`keen-graphics`) or `keen6-14` (covers) and `kdreams113`.

### Title screens

```sh
cd src-tauri
KEEN_GAMES=<absolute path to .local/games>   cargo test -p keen-graphics corpus -- --ignored
KEEN_MODS=<unpacked mods, one folder each> KEEN_GAMES=… KEEN_OUT=<folder>   cargo test covers::tests::mods -- --ignored
```

The first checks that every game's title is a full, colorful 320x200 picture.
The second extracts the title of every mod on top of its game into `KEEN_OUT`
as PNG; look at them. `pnpm test:all` unpacks the mod cache for it into
`src-tauri/target/covers-mods` and writes to `target/covers-out`. To render a
single title: `cargo run -p keen-graphics --example title -- <out.png> <mod
folder> <game folder>`.

### Shareware mirrors

```sh
cd src-tauri && cargo test free_games -- --ignored
```

Downloads every mirror in the shareware manifest and checks that it holds the
expected version. Run it after changing the manifest.

### DOSBox download and launch

```sh
cd src-tauri
BLOOGBASE_E2E_GAME=<folder with a Keen game>   cargo test download_import_and_launch -- --ignored --nocapture
```

Downloads the managed DOSBox Staging, imports the game into a data folder
with a non-ASCII path, starts it for eight seconds and checks the play time
was recorded.

### Mods in DOSBox

Launches every mod in DOSBox on every game version it fits, keeps it running
for a few seconds and saves a screenshot of the DOSBox window. Windows only
for now.

Folder layout (both ignored by git):

```
.local/games/<any name>/   one folder per game copy (folders with several
                           episodes in subfolders work too)
.local/mods/*.zip          the mod archives (the corpus cache)
```

```sh
cd src-tauri
BLOOGBASE_E2E_DOSBOX=<path to dosbox.exe> \
  cargo test e2e_mods -- --ignored --nocapture --test-threads=1
```

Screenshots land in `src-tauri/target/e2e-mods/shots/`. Look at them: "running"
only means DOSBox was still open after seven seconds. A mod patched onto the
wrong game version can still be running, just showing garbage.

## Mod index

The index (`index/`, see `index/README.md`) has its own checks:

```sh
pnpm index:check                       # entries + downloads (cached in .local/mods/index-cache)
cd index/tool && cargo test            # the tool itself
```

CI (`.github/workflows/index.yml`) runs both on every change to `index/` and
weekly, then also asking the servers whether each download still exists. The
app side (signature, cache, ETag, install from the index) is covered by the
unit tests in `src-tauri/src/mod_index.rs` and `src-tauri/src/mods.rs`.
